# 06 安全报告 — LifeOS V2.0

> 方法：实测（未授权/伪造/篡改/注入/XSS/非法参数）+ 代码审查。所有测试未造成数据改动。

## 一、实测通过项 ✅

| 测试 | 结果 |
|---|---|
| 无 token 访问受保护接口 | 401 ✅ |
| 伪造/篡改 token | 401 ✅（签名+内存集合双校验） |

## 二、发现问题（按等级）

### P1 — 重大问题

**SEC-P1-1 技能代码包热加载 = 设计内 RCE**
- 位置：`app/skills/api_skill.py` L120-144（write_skill_package）
- 描述：用户提交的 `handler_code` 直接写盘后 `importlib` 热加载执行，零沙箱。技能名仅 alnum 校验防路径穿越，代码本身无限制
- 影响：任何能调用 `/api/skills/package` 的会话 = 服务器任意代码执行
- 缓解现状：端点有 TOTP 会话鉴权；docstring 声明"仅限可信代码"
- 建议：单用户自用可接受但须在文档显著标注；产品化前必须加沙箱/签名白名单

**SEC-P1-2 密钥明文落盘**
- 位置：`data/settings_runtime.json`（AI key、飞书 secret、备份目标密码全部明文）；`data/otp_secret`、`data/session_secret` 无权限位控制
- 影响：拿到 data 目录 = 拿到全部凭据；备份若打包 data 目录会连带泄露
- 建议：至少对 runtime.json 中密码字段做对称加密（密钥由 env 注入）；备份打包时排除 otp_secret/session_secret

### P2 — 一般问题

| 编号 | 问题 | 位置 |
|---|---|---|
| SEC-P2-1 | SFTP 备份 paramiko `AutoAddPolicy`，不校验主机密钥，存在 MITM 风险 | backup.py |
| SEC-P2-2 | PG 端口 5433 绑定 0.0.0.0，局域网可直连（默认密码兜底加剧了风险） | docker-compose.yml |
| SEC-P2-3 | 硬编码兜底密码 `lifeos_pg_2026` 出现在 compose 与 backup.py L30 | 两处 |
| SEC-P2-4 | TOTP 同一码在时间窗内可重放（无 used-code 记录） | auth.py L89-105 |
| SEC-P2-5 | 登录限流信任 X-Forwarded-For，可伪造 IP 绕过 | main.py L137 |
| SEC-P2-6 | /api/auth/otp-reset 无会话可达（白名单前缀） | main.py L321 |
| SEC-P2-7 | 会话纯内存，重启失效且无主动吊销 | auth.py L38 |
| SEC-P2-8 | 前端 token localStorage 明文，XSS 可窃取（SPA 常见取舍） | frontend/src/api.js |
| SEC-P2-9 | /api/models/fetch 任意外部 base_url，SSRF 探测面 | main.py L820 |
| SEC-P2-10 | FTP 备份为明文协议 | backup.py |

### P3 — 优化建议

- `lark-oapi`/`segno` 未锁上限版本；建议全量跑 pip-audit
- loader.py/db_store.py 用 print 代替 logging，安全事件不可收集
- 建议为 backup/restore、skills/package 等高危端点增加二次确认或独立审计日志

## 三、总体评价

LifeOS 的**认证主链路（TOTP+签名令牌+限流）实现质量高于常见个人项目**，注入与 XSS 防线实测有效。风险集中在两点：密钥明文落盘、技能热加载无沙箱——两者都被"TOTP 单因子 + 单用户自用"这一前提包裹着。只要不暴露到公网无 Tunnel 保护的路径、不转为多用户产品，当前风险可控；一旦产品化，P1 两项必须先解决。

**安全评分：68/100**
