# 02 架构验收报告 — LifeOS V2.0

## 一、代码结构

```
LifeOS/
├── app/
│   ├── main.py          # 1318 行，全部路由+中间件+lifespan（单文件偏重）
│   ├── auth.py          # TOTP + 签名会话令牌
│   ├── config.py        # dataclass Settings，env > runtime.json 覆盖
│   ├── agent/router.py  # Agent 意图分类→技能/多步编排/默认对话
│   ├── ai/              # client/model_presets/registry/usage_store/ratelimit/news_ai
│   ├── memory/          # working(进程内)/short(Redis)/vector(Qdrant)/manager(编排)
│   ├── skills/          # loader/api_skill/store/db_store（技能热加载）
│   ├── backup.py        # pg_dump/redis-cli/qdrant tar + 多协议传输 + 每日调度
│   ├── connector.py / feishu.py / feishu_deviceflow.py
├── frontend/            # Vue3 + Vite，10 组件
├── skills/              # 代码技能包目录（如 amap）
└── docker-compose.yml   # 数据层 3 容器 + api 镜像定义（api 实际跑宿主）
```

**评价**：模块按职责切分清晰（ai/memory/skills/backup 各自成包），分层合理。主要问题是 `main.py` 承载全部 60+ 端点，1318 行已接近可维护性拐点，建议按域拆 router（auth/memory/backup/models/skills）。

## 二、技术架构

- **形态**：单体应用 + 前后端分离（后端同源托管 SPA dist，SPA catch-all 在 main.py L1300）
- **AI 架构**：无 function-calling 协议，自研「JSON 意图分类 → 技能名匹配 → 多步计划（MAX_PLAN_STEPS=4）」，异常全部降级不卡死，符合个人系统容错取向
- **数据架构**：PG（事务数据）/ Redis（短期记忆）/ Qdrant（向量经验）/ 文件（runtime 配置、OTP 密钥）四元存储，职责分明

## 三、依赖分析

| 项 | 结论 |
|---|---|
| 版本锁定 | 主依赖全部强锁（fastapi/uvicorn/pydantic/httpx/redis/sqlalchemy 等），符合规范 |
| 未锁上限 | `lark-oapi>=1.0.6`、`segno>=1.6.1` 仅下限，存在供应链漂移风险（P3） |
| 版本新旧 | 普遍为 2024 年底版本，偏旧但一致；建议跑 pip-audit 复核 starlette/httpx CVE（P3） |
| 前端依赖 | package-lock.json 存在可复现；`dompurify ^3.1.6` 松散版本，其余精确 |

## 四、架构限制（如实记录）

1. **单用户硬编码**：`DEFAULT_USER="me"` 贯穿全库与 REST 入口（main.py L485/L1150），无多租户隔离——对个人系统是合理取舍，对未来产品化是天花板。
2. **进程内存态**：会话集合（VALID_TOKENS）、限流窗口、working memory 全在进程内存，**无法水平扩展**，重启即丢会话。
3. **无迁移工具**：建表靠 `Base.metadata.create_all`，字段演进无 Alembic 版本管理。
4. **重复代码**：`mask_secret`/`_is_valid_key` 三处各抄一份；`_default_chat` 与流式版约 80 行近乎复制。

**架构评分：78/100** —— 分层清晰、取舍自洽，扣分在单文件巨路由、内存态不可扩展、无迁移管理。
